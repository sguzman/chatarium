# Protocol observation changelog

This file records changes in **our observations** of the ChatGPT web client. It is not a changelog published by OpenAI.

## Unreleased

- Established the protocol corpus structure and capture discipline.
- Added first empirical snapshot `2026-09-29.001` from a manual Edge/Linux HAR of a completed new-conversation text turn.
- Observed `/backend-api/f/conversation/prepare` -> `/backend-api/f/conversation` conduit-token linkage, Sentinel material linkage, `text/event-stream` mutation response transport, conversation-topic websocket completion notifications, and persisted reconciliation through `/backend-api/conversations/batch`.
- Recorded that exported HAR did not preserve the SSE body and that DevTools "sanitized" output still contained secret-bearing and private material; raw HAR remains outside Git.
- Added a sanitized structural send-request fixture and cross-snapshot send-text flow document.
- Added canonical C03 snapshot `2026-09-29.002` from Flight Recorder v0.5.0 with the full `/backend-api/f/conversation` response stream.
- Observed SSE `delta_encoding = "v1"`, incremental delta operations, final-message completion patching, `message_stream_complete`, and terminal `[DONE]`.
- Flight Recorder v0.5.1 now treats `[DONE]` as a clean local terminal condition instead of reading once more and reporting Chromium's post-terminal clone abort.
- Added partial controlled C01 snapshot `2026-09-30.001` from Flight Recorder v0.7.0: observed a paginated `/backend-api/gizmos/snorlax/sidebar` JSON surface with nested conversation summaries during sidebar scrolling. The evidence is committed with placeholder-only structure, while `ConversationList` remains `NoBaseline` because the capture does not prove complete account-wide enumeration.
- Added controlled C02 snapshot `2026-09-30.002` from Flight Recorder v0.7.1: three existing-conversation navigations produced the same `GET /backend-api/conversations/<id>` request shape with `include_has_versions` and `num_turns`, but every captured conversation-fetch response was HTTP 429. The request path is now evidence-backed; the successful response schema and `ConversationFetch` baseline remain `NoBaseline`.
- Added canonical successful C02 snapshot `2026-10-01.001` from Flight Recorder v0.7.1: one controlled existing-conversation navigation produced a successful `GET /backend-api/conversations/<id>` response with the same `include_has_versions` and `num_turns` query-key shape, HTTP 200 JSON, and a top-level conversation envelope containing message records and `page_info`. The public fixture preserves only placeholder-only structural shape, and `ConversationFetch` is now `ValidatedAgainst("2026-10-01.001")`. The earlier rate-limited C02 snapshot remains historical evidence.
- Added `2026-10-03.001` from a manual Edge 153/Linux HAR: the successful C02 GET establishes the exact safe query occurrence order `num_turns=10&include_has_versions=true`, corroborates the message-array/current-node/page-info envelope, and adds a newly observed `content_type + thoughts + source_analysis_msg_id` message-content shape. The same HAR also observes successful new-conversation prepare/send/rename behavior, but no second send into an existing thread; same-thread write semantics remain explicitly unestablished. Raw HAR/account/conversation/security material remains outside Git.
- Retrospective comparison of that HAR against the later account-history bridge identified a critical first-party context dependency that the initial C01 reproduction omitted: ordinary `/backend-api/conversations` requests carry a `ChatGPT-Account-ID` request header. The private identifier value is not committed. This observation changes the protocol discipline: request-header presence/classification is now part of request parity, not an implementation detail to ignore.
- Correction after the first live Edge-bridge run: the 2026-10-03 HAR established the **request shape and first-party context** for ordinary global `/backend-api/conversations?...limit=20&offset=0`, but both captured global-list responses in that HAR were HTTP 429. It therefore did **not** establish successful C01 result semantics. Successful conversation-list-like HTTP 200 responses in the same HAR were on gizmo/project surfaces such as `/backend-api/gizmos/<id>/conversations` and `/backend-api/gizmos/snorlax/sidebar`; those must not be conflated with account-wide ordinary history.
- C01 profile `2026-10-03.003` changes the browser compatibility strategy from reconstructing a request from URL + account selector to replaying the **currently observed first-party application request context**. The Edge extension observes only a narrow allowlist of application-controlled headers on the exact C01 request, keeps their values in `chrome.storage.session`, and returns only safe proof metadata (context observed, original first-party HTTP status when available, and replay-header count). Raw header values, account identifiers, cookies, authorization material, and browser storage never cross into Rust.
- Final live validation of `2026-10-03.003` falsified exact-C01 replay as a runtime strategy. Edge Bridge 0.2.0 observed a valid ChatGPT tab and account context both before and after a full tab reload, but never observed the exact frozen ordinary-history request: `request-context=no`, `first-party-http=unknown`, `context-headers=0`, `first_party_request_context_unavailable`. No C01 baseline is promoted from this failure.
- Edge Bridge 0.3 replaces fixed-request replay with bounded CDP history-surface discovery. It attaches only to the selected ChatGPT tab, enables the Network domain, reloads the tab automatically, observes current successful JSON `/backend-api/*` traffic, reads completed list-like candidate bodies, and reduces them to typed conversation summaries plus structural pagination evidence before returning anything to Rust. Candidate discovery remains non-canonical evidence: `ConversationList` stays `NoBaseline` until completeness and pagination are separately established.
- First live Edge Bridge 0.3 validation succeeded at the discovery boundary: one bounded automatic reload yielded 85 real conversation summaries/titles in the desktop. The count is an observed set, not a proven account total; no `ConversationList` baseline is promoted.
- The same live run then exposed a separate C02 transport defect: clicking one discovered conversation caused the old synthetic MAIN-world exact read to time out. Edge Bridge 0.4 changes the capture mechanism to first-party browser navigation in a temporary background tab with CDP attached before navigation. The existing `2026-10-03.001` C02 semantic profile and exact-ID parser remain the validation authority; the change does not create a new response-semantic baseline.
- The Tampermonkey account-history bridge is retained only as historical engineering evidence. One v0.3 live run proved browser↔desktop roundtrip plus authenticated page execution but returned a semantically implausible empty history; v0.4 attempted browser-local account-context preservation and then regressed to no loopback traffic in the target environment. The exact regression cause is unknown. No protocol baseline is promoted from those failed runtime experiments.
