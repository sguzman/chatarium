# Chatarium Edge Bridge

This directory contains the **critical-path browser runtime** for Chatarium's read-only interoperability with the user's existing ChatGPT conversation corpus.

It replaces three failed/retired assumptions:

1. Tampermonkey as critical transport;
2. reconstructing a frozen ordinary-history request;
3. waiting for that exact historical request to appear before replay.

The Flight Recorder elsewhere in `browser/` remains a separate durability/evidence tool.

## Current architecture: 0.4.3 first-party CDP observation

```text
Chatarium Desktop
    ↕ typed HTTP loopback on 127.0.0.1:43117
Edge MV3 extension service worker
    ↕ bounded chrome.debugger attachment
authenticated ChatGPT browser context
    ↕ Chrome DevTools Protocol Network domain
actual first-party /backend-api/* traffic
```

The architectural rule is now simple:

> Observe the request/response ChatGPT actually performs instead of synthesizing an undocumented private request when a first-party navigation can produce it.

## History discovery

History discovery does not assume that one historical conversation-list endpoint will appear.

For one bounded discovery command, the extension:

1. finds one authenticated `https://chatgpt.com/*` tab;
2. attaches `chrome.debugger` to that tab;
3. enables the CDP Network domain;
4. reloads the tab itself;
5. observes the actual current first-party network responses generated by ChatGPT;
6. considers only HTTP 200 JSON responses under `/backend-api/` whose paths are conversation/sidebar/pin-like;
7. waits for candidate responses to finish;
8. reads bodies with `Network.getResponseBody`;
9. applies response-size and JSON-traversal bounds;
10. extracts typed conversation-summary candidates and safe structural metadata;
11. detaches the debugger.

The extension does **not** invent or replay a global conversation-list request.

### First live result

Edge Bridge 0.3.0 passed its first live browser validation on 2026-10-03.

The observer populated Chatarium with **85 real conversation summaries/titles** from the first-party traffic emitted during the bounded reload window.

This proves that live CDP history-surface discovery works.

It does **not** prove that 85 is the account-wide total. The desktop therefore displays:

```text
CHATGPT HISTORY · 85 OBSERVED
```

rather than `85/85`, and the History discovery status explicitly says coverage is unknown.

## Exact conversation mirroring

The first 0.3 live run also exposed the next downstream boundary: clicking one discovered conversation fell back to the older synthetic MAIN-world C02 fetch and eventually produced a generic bridge timeout.

0.4.0 removed that mismatch.

For a discovered conversation, the extension now:

1. confirms an authenticated ChatGPT tab/account context already exists;
2. creates a temporary **background** browser tab;
3. attaches CDP before the target navigation;
4. enables the Network domain;
5. navigates the temporary tab to `https://chatgpt.com/c/<remote-id>`;
6. watches for the exact first-party `/backend-api/conversations/<remote-id>` response generated by ChatGPT itself;
7. preserves the actual HTTP status and JSON content type;
8. waits for response completion;
9. reads the body with `Network.getResponseBody`;
10. applies the 4 MiB body bound and JSON validation;
11. returns the private body only to the local Rust process;
12. lets the existing evidence-gated C02 parser verify the exact remote conversation identity;
13. lets the existing append-only store commit the durable local mirror;
14. detaches the debugger and closes the temporary tab in all outcomes.

The user's active ChatGPT tab is not navigated away from the current conversation.

### 0.4.1 discovery-regression repair

The first 0.4.0 live run exposed a regression in history discovery: the extension still observed network traffic, but only one zero-item `/backend-api/conversation/init` candidate survived classification, so the desktop lost the previously proven 85-chat result.

The exact causal delta was not established. Two discovery-path changes had been made while adding mirroring: the debugger event listener was multiplexed with exact-mirror capture, and the proven discovery completion/grace sequence was replaced with a new bounded settle helper.

0.4.1 fixes this without guessing which change was causal:

- restores the exact known-good 0.3 discovery `onEvent` / `onDetach` implementation;
- restores the exact 0.3 discovery completion/wait sequence;
- moves exact-mirror capture into separate debugger listeners keyed only by mirror capture sessions;
- keeps the bounded settle helper only on the new mirror path;
- renders a zero-item pass as `DISCOVERY INCOMPLETE`, never green `DISCOVERED`;
- retains previously observed in-memory conversation summaries when a later pass is sparse instead of replacing the catalog with zero.

The 2026-10-03 C02 protocol profile remains the semantic validation profile. 0.4 changes **how the first-party response is obtained**, not the parser's right to invent new semantics.

### 0.4.2 / 0.4.3: deterministic recovery of the proven 85-chat surface

A second live run of 0.4.1 still produced zero observed conversations even though the exact 0.3 listener and wait logic had been restored. That established that the original 0.3 success was real but opportunistic: the passive observer only succeeds when the frontend itself happens to request a list-bearing surface during the bounded reload window.

The private HAR already contains stronger evidence. It records HTTP 200 for:

`/backend-api/gizmos/snorlax/sidebar?conversations_per_gizmo=5&limit=20&owned_only=false`

with an approximately 185 KiB JSON body containing nested conversation summaries and top-level/nested cursors. The same HAR records subsequent cursor pagination requests on that sidebar surface.

0.4.3 therefore keeps the **entire known-good 0.3 passive classifier and debugger listener unchanged** and adds a deterministic fallback:

1. run the original bounded passive 0.3 discovery;
2. if that pass yields one or more conversations, stop there;
3. only when the passive pass yields zero conversations, reuse browser-local application context observed from ordinary first-party backend traffic;
4. issue one bounded MAIN-world GET for the known successful sidebar resource;
5. reduce its response through the same 0.3 conversation-summary classifier;
6. merge the summaries into the discovery result;
7. expose only safe proof metadata to Rust: whether bootstrap ran, HTTP status, item count, application-context header count, and a non-secret error code.

Raw application-context header values never cross into Rust.

This bootstrap is intentionally a **fallback**, not a replacement for the working 0.3 path. It cannot perturb a naturally successful passive discovery.

## Explicit mirror states

History discovery and per-conversation mirroring are separate status domains.

History:

- discovering;
- discovered / N observed;
- coverage unknown;
- discovery failed.

A discovered conversation:

- discovered · click to mirror;
- mirroring;
- exact response captured / validating;
- persisting durable mirror;
- fully mirrored locally;
- mirrored locally · partial, when older content is known to exist;
- mirror failed · click to retry.

A failed individual mirror must never turn a successful history discovery into `PROOF FAILED`.

## Why 0.1/0.2 were retired

Edge Bridge 0.1.0 proved the purpose-built extension transport itself worked: desktop roundtrip, ChatGPT tab selection, MAIN-world execution, authenticated session, account context, HTTP success, and Rust parsing.

Its reconstructed ordinary-history request still returned an implausible empty result.

Re-auditing the private 2026-10-03 HAR showed that the captured ordinary global `/backend-api/conversations?...limit=20&offset=0` requests were HTTP 429. The artifact therefore established request shape/context, not successful ordinary-history semantics.

0.2.0 made the one allowed evidence-driven correction: wait for the exact first-party frozen request and replay its observed context.

The final 0.2 validation failed both before and after a full ChatGPT-tab reload:

```text
tab=yes
account-context=yes
request-context=no
first-party-http=unknown
context-headers=0
first_party_request_context_unavailable
```

The runtime dependency itself was invalid, so exact-C01 replay was retired.

## Permissions

The 0.4.3 manifest contains only:

- `debugger`
- `scripting`
- `storage`
- host access to `https://chatgpt.com/*`
- host access to `http://127.0.0.1:43117/*`

No new broad permission was added for temporary-tab mirroring. Chrome/Edge's Tabs API allows extension service workers to create, navigate, and close tabs without the broad `tabs` permission; that permission is primarily required for access to sensitive tab metadata such as arbitrary URL/title fields.

The `debugger` permission is powerful and intentionally explicit. Chatarium uses it only for bounded ChatGPT observation/capture sessions and detaches in cleanup paths.

Do not add cookies, browsing-history, `<all_urls>`, or arbitrary-tab capture merely for convenience.

## Credential and private-data boundary

Reusable authentication material does not cross into Rust.

The extension does not return:

- cookies;
- `Authorization` values;
- full request-header sets;
- browser storage;
- reusable session secrets.

During discovery, `ChatGPT-Account-ID`, when observed, may be retained only in `chrome.storage.session` as safe proof that the browser account context exists. The exact 0.4 mirror capture relies on first-party browser navigation rather than manually replaying that header.

History candidate response bodies are reduced in the extension to typed conversation summaries plus structural metadata before crossing loopback.

An exact conversation body is private user content and intentionally crosses into the local Rust process only for exact-ID validation and durable local mirroring. It is never committed to public protocol fixtures.

## Supported commands

The loopback wire protocol remains version 1.

Current commands:

- `probe_auth`
- `discover_history_surfaces`
- `fetch_conversation`

`list_conversations` remains only as an explicit retirement response so stale desktop code cannot silently revive exact-C01 replay.

Current profiles:

- authentication probe: `chatgpt-me-v1`
- history-surface discovery: `cdp-history-discovery-v1`
- exact C02 semantic validation: `2026-10-03.001`

## Discovery proof

A successful discovery result exposes safe proof for:

- extension version;
- desktop roundtrip;
- exact ChatGPT tab found;
- debugger attached;
- Network domain enabled;
- automatic tab reload started;
- network responses observed;
- successful `/backend-api/` responses observed;
- list-like JSON candidate responses;
- response-body read failures;
- oversized/malformed body rejection;
- candidate surface/item counts;
- browser-local account context when observed.

Candidate discovery does not claim account-wide completeness.

## Mirror proof

A successful exact mirror carries separate proof:

- authenticated source ChatGPT tab found;
- browser-local account context present;
- temporary capture tab created;
- debugger attached to that temporary tab;
- Network enabled;
- first-party navigation started;
- exact remote-conversation response observed;
- actual first-party HTTP status;
- response body read and JSON parsed;
- exact remote ID validated by Rust;
- durable local mirror event committed;
- partial/complete transcript state reported.

A generic timeout is not an acceptable terminal diagnostic when a specific capture stage is known.

## Loopback

The service worker talks only to `127.0.0.1:43117` and sends `X-Chatarium-Bridge: edge-mv3-v1`.

Chatarium independently:

- binds loopback only;
- rejects ordinary web origins/preflight;
- accepts the Chromium extension-origin shape;
- enforces request-size limits;
- correlates command/result IDs;
- rejects the retired userscript bridge marker.

Native Messaging is not used.

## Human QA gate

Before each browser validation:

- extension syntax and manifest invariants must pass;
- history-classifier tests must pass;
- exact-conversation matcher tests must pass;
- Rust format/check/tests must pass;
- Linux desktop check/tests must pass;
- the issue must state exactly what the run can prove.

History discovery performs its own reload. Exact mirroring performs its own temporary-tab navigation and cleanup. The operator should not need DevTools, console inspection, manual tab traversal, or another HAR merely to exercise these paths.

Follow `docs/HUMAN_QA.md`, #103 for discovery history, and #104 for exact mirroring.
